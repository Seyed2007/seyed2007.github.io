PROJECT / 01Home lab

Raspberry Pi VPN Gateway · Homelab

A two-exit-node Tailscale setup for learning how remote access, DNS filtering, firewall policy, and internet egress fit together across a home network and a cloud VM.

EGRESS / 02 HOME ↔ CLOUD

Overview

I configured a Raspberry Pi at home as a Tailscale exit node. Pi-hole provides DNS filtering for configured clients, while Linux firewall rules help control traffic at the host. A separate Oracle Cloud VM in Frankfurt provides a second exit-node choice.

My implementation

The two routes share the Tailscale network but send internet-bound traffic through different egress points. Selecting the Pi uses the home connection and its Pi-hole DNS path; selecting the Frankfurt VM sends that traffic out through the cloud host.

PROJECT / 02Research pipeline

StreamScope · Automated RTSP Discovery and Verification

A staged network-camera research workflow that treats Shodan records as leads, filters discovered services, and checks which candidate endpoints respond to RTSP verification within an authorized research scope.

RTSP / 554 DISCOVER / VERIFY

Problem

Raw internet scan data can contain irrelevant services, stale records, and endpoints that do not behave as expected when checked directly. The useful work is narrowing that data into findings that can be reviewed, with each stage kept distinct.

My implementation

The workflow processes Shodan-sourced targets, discovers candidate services, inspects and filters noisy results, performs RTSP verification, retains useful findings, and hands appropriate results to a monitoring view.

Investigation flow / candidate to reviewable finding
  1. Shodan dataStart from research records, treated as candidate leads.
  2. Target processingPrepare the input set for the next checks.
  3. Service discoveryIdentify candidate network-camera services.
  4. Inspection and analysisGather response context for candidate endpoints.
  5. Noise filteringRemove irrelevant or unhelpful results.
  6. RTSP verificationCheck endpoint behavior against the RTSP stage.
  7. Result storageRetain findings for later review.
  8. Live monitoringUse a viewer only within authorized scope.

Discovery

A network service response makes an endpoint a candidate for further inspection. It does not establish that a camera stream is usable.

Verification

An RTSP check records how an endpoint responds to the project’s verification stage. It is distinct from broad service discovery.

Authorized access

Access to any stream requires explicit permission and a defined scope. A public response is not permission to view or retain footage.

An exposed RTSP service alone does not establish usable camera access or authorization; any interaction requires explicit permission and a defined scope.

PROJECT / 03Automation

Automated IP Research Pipeline

A recurring data-processing system that turns Shodan IP datasets into validated, deduplicated, enriched, scored, and ranked candidates—so investigation can focus on relevant services such as TCP/554.

BATCH / 03D TRIAGE / RANK

Overview

New research data is collected approximately hourly and organized into three-day batches. The pipeline separates collection, quality checks, enrichment, and prioritization so repeated or irrelevant records do not consume the same review effort as higher-priority candidates.

System architecture / intake to review queue
INPUT / SCHEDULEDShodan datasetsApproximate hourly collection; fixed three-day research window.
PROCESS / CONTAINERDocker worker poolParallel workers with configured resource limits and error handling.
STATE / PERSISTENTSQLiteRetains pipeline state for deduplication and restart/resume.
VISIBILITY / REVIEWLive terminal dashboardCollection progress, worker limits, runtime health, and batch status.

Data workflow / nine stages

Filter early; spend deeper checks where they add context.

  1. 01 / COLLECTIONReceive new datasets

    Bring in the latest research input.

  2. 02 / VALIDATIONCheck target records

  3. 03 / DEDUPLICATIONRemove repeats

    Avoid reprocessing duplicate IPs or records.

  4. 04 / TRIAGEApply research criteria

    Narrow the candidate set, such as by TCP port.

  5. 05 / ENRICHMENTAdd service context

    Attach information needed for useful review.

  6. 06 / HTTP + TLSInspect web services

    Analyze applicable HTTP and TLS characteristics.

  7. 07 / SCORINGApply configured rules

    Represent research priority using implemented criteria.

  8. 08 / DEEPER ANALYSISCheck selected candidates

    Reserve additional checks for triaged records.

  9. 09 / RANKINGOrder findings

    Present higher- and lower-priority review candidates.

Why deduplication is separate

It prevents repeated addresses or records from creating avoidable downstream work and helps the persistent state support restart and resume.

Why triage and enrichment are separate

Triage narrows the work by configured criteria; enrichment adds context to the candidates that remain, including applicable HTTP/TLS details.

How to read a score

A score and rank are prioritization signals based on configured criteria. They are not proof that a vulnerability exists.

The pipeline is designed to turn recurring raw datasets into a prioritized review queue. Any score remains a triage aid and requires manual validation in an authorized scope.

PROJECT / 04Lab tested

ReconX · Network Discovery and Security Analysis

A Python reconnaissance tool that wraps a focused Nmap run in a Rich terminal workflow, adds service and TTL context, associates configured risk references, and produces portable JSON and TXT reports.

TCP / TOP 15 SCAN / REPORT

Overview

The user supplies an IP address or hostname in an authorized environment. ReconX resolves the input, scans its configured top 15 TCP ports, and turns Nmap’s open-port and service data into a structured review.

  1. Target input and resolutionAccept an IP or domain and resolve the hostname to an address for the run.
  2. Port and service discoveryRun Nmap against 15 configured TCP ports and parse open-service details.
  3. Context gatheringCollect short service banners concurrently and estimate an OS from a ping TTL heuristic.
  4. Risk interpretationShow configured port/service risk levels, CVE references where listed, and follow-up checks.
  5. Report generationDisplay a summary and save the scan record in JSON and TXT formats.

What the Python layer adds

It coordinates the scan, parses Nmap XML, gathers banners concurrently, formats phases and results through Rich, and assembles the terminal summary and reports. The live scan display shows elapsed time while Nmap runs.

View ReconX repository ↗

Risk and CVE references

Risk labels and CVE references come from configured per-port entries. They are not matched to a validated product version, and an open port or reference is not a confirmed vulnerability.

OS estimate

TTL-based identification is heuristic and can be affected by network hops or host configuration. Treat it as an estimate for follow-up.

Validation and scope

Suggested checks are leads for manual review on systems with permission. The scan output alone does not establish exploitability.
